# 为什么检索到的事实到不了你的 Agent

[English](the-render-gap.md) | **中文**

> 记忆层检索到了正确的事实，模型却还是答错——因为那条事实**根本没进提示词**。我们称之为 **render gap（渲染鸿沟）**：从「检索到」到「模型看见」之间，一步「排序 + 预算」会悄悄丢掉证据。本文讲我们怎么找到它，并附一个能跑的 A/B 复现机制。

## TL;DR

- **症状**：检索命中正确答案，模型却拒答或编造。
- **机制**：渲染时把**所有**事实按 `valid_from` 全局最新优先排序，再加字符预算。**旧但相关**的答案事实被排到后面、被丢弃，模型根本没看到。
- **修复**：按召回相关度渲染；recency 只在**同主题内**做冲突裁决。
- **证据范围**：下面的可跑 demo 确定性地复现**渲染**机制。我们日志里的采纳数字（单题 0/5→5/5）是**示意，不是统计结论**（单题、重复不独立）——见[局限](#局限)。

## 背景

一个 agent 记忆层：项目事实存台账；回答前检索 top-k 并渲染进上下文。典型问题：

> 「如果自动导出路线坏了，现在可用的两条构建路径是什么？」

库里有条事实 `build-pipeline`（合成）写明答案：「两条路：CLI 全自动 + 编辑器半自动」。检索命中了它，模型却说「不知道」或编一条。

关键洞察：**检索命中 ≠ 事实进入提示词。** 中间还隔着一层渲染。

## 排查

我们用隔离实验（关自动注入、手动控制上下文）测了一系列假设。在所测条件下，这些都没能解释失败：

| 假设 | 实验 | 观察 |
|---|---|---|
| 事实文本太长 | 只给目标事实 | 答对 |
| 干扰事实混淆 | 目标 + 干扰，内联 | 答对 |
| 目标位置靠后（内联） | 内联放最后 | 答对 |
| 注入头措辞/不信任 | 权威 vs 谨慎措辞 | 无观察到差异 |
| 独立消息投递 | 改消息位置 | 无观察到差异 |
| 工作区指令让它去读文件 | 换中性指令 | 无观察到差异 |

这些是**特定条件下的阴性结果**，不是普适排除。浮现的规律：**事实内联紧挨问题时模型会用；走真实管道却常常不用。** 没控制的变量是**库的内容**。

## 决定性观察：到底渲染了什么

我们把 `included_ids`（实际渲染）和 `recalled_ids`（检索返回）分开记录：

| store | 渲染进上下文 | 答案在? |
|---|---|---|
| 小（5 条） | `build-pipeline`, … | **在** |
| 大（20 条） | `report-gen`, `media-svc`, … | **不在——被丢** |

事实更多后，答案仍被**检索到**，却不再被**渲染**。这就是 render gap。

## 机制

```ts
// 召回已按相关度排好：facts[0] 最相关
const ordered = facts.sort(byValidFromNewestFirst);  // ← 摧毁相关度顺序
let size = header.length;
for (const f of ordered) {
  if (size + f.text.length > MAX_CHARS) continue;    // 超预算：跳过
  render(f); size += f.text.length;
}
```

两个设计叠加出事：
1. **全局最新优先重排**：本意「冲突信新的」，实际把**每条**事实按日期重排，丢掉相关度。
2. **字符预算**：前面的占满，后面的被跳过。

答案事实恰是库里**最旧**的，于是更新的干扰排前面、占满预算，它被跳过。

## 修复

**相关度主序；recency 只做同主题内裁决：**

```ts
const firstIdx = new Map(); // 每个 subject 的最早召回位置
facts.forEach((f, i) => { if (!firstIdx.has(f.subject)) firstIdx.set(f.subject, i); });
const ordered = facts.sort((a, b) => {
  const ga = firstIdx.get(a.subject), gb = firstIdx.get(b.subject);
  if (ga !== gb) return ga - gb;      // 主题间：相关度
  return recency(b) - recency(a);     // 主题内：新的在前
});
```

旧但相关的事实保住它的相关度位置；同主题冲突仍优先新版本。（注意：「同主题」只是「可能冲突」的启发式，不是保证；「更新」也不必然「更正确」。）

## 可跑 A/B（复现机制，不是采纳结论）

[`eval-methodology/reference/render_relevance_first.py`](../eval-methodology/reference/render_relevance_first.py) 同时实现 buggy 和 fixed 渲染器，返回 `included_ids` **和 `dropped_ids`**。用「最旧答案 + 更新干扰」的合成集：

```
buggy included: ['d3', 'd2']   dropped: ['d1', 'answer']
fixed included: ['answer', 'd3'] dropped: ['d1', 'd2']
```

buggy 丢掉答案，fixed 保留。这确定性地复现了**渲染**机制——不涉及模型。

## 我们日志里观察到的（示意，非证明）

在私有环境、这一道题上，修复恰逢答案采纳从 0/5 到 5/5。**我们把它作为机制示意，不是普适结论：**

- 这是**单题**、各 5 次。单题的重复**不独立**，因此**不适用任何显著性检验**，我们对该翻转**不做统计断言**。（McNemar 要求独立的配对题；见 SPEC。）
- 修复同时改了**排序**和**答案位置**（它变成第一条渲染）。我们**没做**第三格对照（大库 + 强制保留答案），无法把位置效应和排序效应分开。
- 此处不披露模型/版本/解码参数和 `MAX_CHARS`，因为那些日志来自私有环境；请把这些数字当轶事。

站得住的结论是**机制**（上面已复现），不是采纳差值。

## 局限

- 修复**只是换了排序键，没有消除预算驱动的丢失**。大条相关事实仍可能被跳过、小条无关事实仍被渲染；靠前的主题组仍可能占满预算。返回 `dropped_ids` 让这**可审计**，而非不可能。
- 「同主题⇒冲突」「更新⇒正确」是启发式，不是保证。
- 渲染 demo 是确定性的；采纳需要模型 + 语料，本文不复现。
- 日期假设 ISO-8601；参考实现拒绝其它格式，而非静默错序。

## 相关工作

agent 记忆系统对「什么进提示词」各有方案：MemGPT/Letta（OS 式分页）、Mem0（事实抽取）、Zep/Graphiti（时序知识图谱）、LangMem，以及 Basic Memory 等本地优先 Markdown 存储。render gap 与检索质量正交：即便检索器完美，证据仍可能被渲染/预算步骤丢掉。据我们所知这一具体失效模式讨论较少，欢迎指正已有工作。

## 带走三点

1. **「检索到」≠「模型看见」。** 审计实际渲染了什么（`included_ids`）**以及丢了什么**（`dropped_ids`），不只是召回了什么。
2. **「冲突信新的」≠「全局按时间重排」。** 局部裁决和全局排序是两码事，后者牺牲相关性。
3. **隔离实验胜过直觉——但注意样本量。** 几个「听起来对」的假设都没通过检验，根因藏在排序里。而单题翻转是机制演示，不是显著结论。
